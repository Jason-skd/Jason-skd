# AI 工作流治理

本文规定 AI 在本仓库从接收任务到交付结果的默认流程。它约束工作方法，
不扩大用户授权的目标或写入范围。

## 1. 判断任务类型

先区分任务属于哪一类：

- 咨询、解释或方案讨论；
- 只读调查、诊断或评审；
- 功能实现、缺陷修复或重构；
- 文档、发布、运维或远端资源操作。

只读任务在证据和结论处停止。实现类任务在授权范围内完成修改和验证，不能只给出
一份未经执行的建议。远端变更、发布和不可逆操作必须分别确认其授权与目标。

## 2. 建立当前证据

开始前确认：

- 当前目录、适用治理和仓库边界；
- branch、revision、worktree、dirty state 和锁定依赖；
- 任务关联的 issue、pull request 或 review 所对应的 revision；
- 仓库契约、相邻实现、调用方、测试和正式验证入口；
- 必要的官方规范、供应商文档或锁定版本源码。

结论可能随代码、分支或依赖变化时，必须检查当前状态。旧日志和旧测试结果不能
证明当前 checkout。

## 3. 推导任务契约

在内部明确以下内容：

```text
目标：需要改变或确认的可观察结果
不做：明确排除以及不应顺带扩张的事项
所有权：负责该行为的模块、协议或外部系统
影响面：代码、数据、接口、测试、生成产物和文档
验收：完成时必须提供的证据
```

这些内容能由当前任务和权威来源推导时直接执行。只有缺失信息会实质改变结果时，
才向用户提出阻塞性问题。

## 4. 读取最小充分上下文

从最接近可观察行为的入口追踪到实际责任层：

```text
入口或 adapter -> 应用编排 -> 领域规则 -> 基础设施或外部系统 -> 测试
```

使用精确搜索定位符号、调用方和测试，排除依赖目录、缓存和构建产物。既不默认通读
整个仓库，也不在只看到局部代码时猜测全局行为。

## 5. 设计并实施完整变更

- 选择满足当前需求的最小完整结构，不为假设性未来需求建立框架。
- 跨层变更先明确各层职责、数据流、错误边界和失败后的副作用。
- 内部契约变化应同时更新全部当前调用方、测试、文档和派生产物。
- 按可验证的小批次推进：契约与类型、核心实现、调用方与 adapter、测试与
  生成产物、文档。
- 每批先运行最相关检查；失败时定位根因、修复并复测，再扩大验证范围。

默认执行链路为：

```text
调查 -> 实施 -> 聚焦验证 -> 修复 -> 扩大验证 -> 最终检查
```

## 6. 处理评审与故障

- 将 review finding 视为需要在指定 revision 上验证的假设。
- 区分仍存在的问题、已经解决的问题、误报和需要产品决策的问题。
- 缺陷修复应在最近的责任层增加能复现原失败模式的回归场景。
- 不为了迎合评论文字而修改正确代码，也不借修复机会进行无关清理。

## 7. 提交纪律

- 默认按可独立审查、可独立回滚的关注点拆分 commit，不把无关变更压入同一个提交。
- 每个 commit 必须保持自身完整，包含使该变更成立的实现、测试和文档，不留下已知的
  编译失败、测试失败或占位状态。
- 每次创建 commit 前，必须核对 `README.md` 的文档索引与仓库现状一致。新增、移动、
  删除文档或改变文档职责时，在同一个 commit 中更新索引。
- 只暂存当前 commit 所属的明确路径，并在提交前检查 staged diff。

## 8. 完成交付

结束前确认：

- diff 只包含授权范围内的完整变更；
- 格式、构建、静态分析、测试、生成同步和文档检查与风险匹配；
- 临时文件、调试代码、凭据和本地产物没有进入变更；
- 无关工作区内容保持原样；
- 任何无法执行的验证及其风险已明确说明。

最终结果应说明改变了什么、关键边界、实际运行的验证及剩余风险。治理规则本身只在
任务明确要求时修改；普通工程任务中发现的治理改进仅作为建议报告，不得顺带写入。
